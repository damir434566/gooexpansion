# Goo Collect — сбор каталога через расширение Chrome

Продолжение блока «добыча» из **PR #863** (`Darakhamia/goo-fashion`): магазины
отвечают отказом нашему серверу на Vercel, но отвечают браузеру администратора.
Руки переносятся на его машину, мозги остаются на сервере.

> **Состояние на 2026-09-26.** Всё отсюда уже влито в `Darakhamia/goo-fashion`
> (PR #864–#878), и этот репозиторий сверен с его `master` @ `eceda65`:
> расширение **1.0.3** и серверная часть сбора — те же файлы, байт в байт.
> Патчи `apply-to-goo-fashion.patch`, `fix-for-goo-fashion-master.patch` и
> `HANDOFF.md` удалены: применять больше нечего. Сайт целиком сюда не
> копируется — только расширение и то, что разбирает и импортирует товар.
>
> Что добавилось в `master` после четвёртого круга и теперь есть здесь:
> - **Цвет** (`colour-choice.ts`, `taxonomy/colours.ts`): расширение шлёт
>   несколько кандидатов цвета (`colorCandidates`), сервер выбирает тот, что
>   правда цвет, а не alt-текст фото свотча или имя файла.
> - **Название** (`piece-name.ts`): читается `<h1>`, хвост магазина из
>   `<title>` отрезается по заголовкам соседних страниц (`pageTitle`).
> - **Бренд из названия** (`brand-from-name.ts`), когда разметка его не называет.
> - **Одна карточка на вещь**: цвета группируются по имени вещи без бренда и
>   цвета, а тот же товар в другом магазине узнаётся и по имени модели
>   («Samba OG»), не только по штрихкоду.
> - **Автозаполнение** стиля, пола, типа вещи по словарям
>   (`taxonomy/styles.ts`, `garments.ts`, `gender.ts`) и по дереву категорий.
> - Миграции **021** (`color_groups` — 13 цветов фильтра) и **022** (пол по
>   умолчанию у магазина).
>
> **Расширение 1.0.4** (сверено с `master` @ `f86722c`, PR #880):
> - свотчи из «Вам может понравиться», «похожих товаров» и карточек других
>   товаров больше не читаются как цвета этого товара — разные куртки не
>   сливаются в одну цветовую группу;
> - `titleText` — название рядом с кнопкой «Add to bag» / «В корзину», для
>   магазинов без разметки, где в `<h1>` логотип (mowalola);
> - `shopify` — на Shopify расширение само читает `/products/<handle>.json` и
>   `/meta.json` со своего домена (название, бренд, все фото, размеры, валюта
>   магазина), таймаут 6 с, при ошибке страница собирается как обычно;
>   сервер принимает это в `collect/route.ts` и `parser/shopify.ts`.
>
> Приёмка: `node verification/goo-collect-checks/check.mjs extension/snapshot.js` — 9/9.

Здесь три круга работы:

1. **Сбор** — расширение, приёмник, план по robots.txt и сайтмапам, вежливый темп.
2. **Фото и цена** — все фотографии вещи вместо тех, что успела смонтировать
   карусель, и цена в одной валюте: гривны, злотые и рубли пересчитываются в
   доллары при импорте. Здесь же ответ, почему именно Farfetch отдавал меньше
   фото, чем остальные магазины — [ниже](#почему-farfetch-отдавал-меньше-фото).
3. **Десять пустых полей** — размеры, цвет, фильтр цвета, описание, материал,
   бренд, категория, подкатегория, стиль, группировка по цвету и «тот же товар
   на другом сайте». Шесть частей, каждая со своими тестами — [ниже](#третий-круг-десять-пустых-полей).

## Что сделано

### Сервер — решает, что собирать

| Файл | Что делает |
|---|---|
| `src/lib/server/parser/robots.ts` | Разбор robots.txt: Allow/Disallow по длиннейшему совпадению (с `*` и `$`), Crawl-delay, Sitemap. Только группа `*` — Googlebot'ом не представляемся. Разбор чистый, сеть не трогает. |
| `src/lib/server/parser/plan-collection.ts` | Чистая функция: страница + сайтмапы + robots → товарные адреса, пауза, что дочитать следующим кругом. |
| `src/app/api/admin/parser/collect/route.ts` | Действия `plan` и `ingest`. `ingest {url, html}` зовёт `parsePage` с готовой разметкой — в магазин не ходит; без `html` отвечает 400, а не фетчит молча. |
| `src/app/goo-studio/parser/collect/page.tsx` | Вкладка-приёмник: мост postMessage ↔ API обычной сессией Clerk, живой ход прогона, исходы по страницам, Stop. |

Ничего не продублировано: `extractProductLinks`, `looksLikeProductPath`,
`isNonProductPath` и хелперы `sitemap.ts` переиспользованы (для этого из
`sitemap.ts` экспортированы `locations`, `isIndex`, `namesProducts`, `rankChild`
и `CANDIDATES`). Заодно исчез дубль: `fromRobots` в `sitemap.ts` разбирал строки
`Sitemap:` сам — теперь зовёт `parseRobots`.

Изменены всего два существующих файла: `sitemap.ts` (экспорты + снятый дубль) и
`audit.ts` (одна строка в union `AdminAction`).

### Расширение — `extension/`, manifest v3

| Файл | Что делает |
|---|---|
| `manifest.json` | `optional_host_permissions`, **не** `<all_urls>`. Content script — только на `/goo-studio/parser/collect*`. |
| `popup.js` / `popup.html` / `popup.css` | Сколько собрать, «Collect this store», прогресс, Stop. Здесь же запрос доступа к домену по клику. |
| `background.js` | Очередь, темп, вкладка → отрисовка → снять DOM → закрыть. Вся вежливость. |
| `snapshot.js` | Санитайзер: скрипты кроме `ld+json`, стили, svg, iframe, data-URI — один в один с `src/lib/parser-bookmarklet.ts`. Сначала прокручивает страницу, чтобы проснулась ленивая галерея. |
| `bridge.js` | Мост между воркером и вкладкой-приёмником. |

**Ключей в расширении нет.** Оно не умеет звать наш API: сессия Clerk
кросс-доменно не поедет, а токен внутри расширения — ключ под ковриком. Оно
говорит с открытой вкладкой приёмника, а та зовёт API вашей обычной сессией.

### Вежливость

- Disallow из robots.txt соблюдается — решает сервер, расширение не может обойти.
- Пауза `max(Crawl-delay магазина, 1.5 с)` + случайный разброс.
- Отдых ~10 с каждые 20 страниц.
- Два ответа 403/429 подряд — остановка с объяснением.
- Stop мгновенный: гасит текущую паузу **и** приёмник перестаёт принимать, так
  что страница «в полёте» уже не долетит до импорта.

## Второй круг: все фото и одна валюта

### Почему Farfetch отдавал меньше фото

Это нашлось в коде, а не угадалось. Сервер добывает адреса фотографий из
инлайновых hydration-payload'ов страницы — в `gallery.ts` для этого есть
отдельный проход, и именно он находит галерею у магазинов, которые не пишут её
в разметку. А `extension/snapshot.js` удаляет **все** `<script>` кроме
`ld+json` до отправки страницы. Дальше всё зависит от того, где магазин держит
галерею:

| Магазин | Где галерея | Что доезжало до сервера |
|---|---|---|
| Shopify и подобные | в разметке, `<img>` и `srcset` | вся |
| Farfetch и любой SPA | в payload'е (`__NEXT_DATA__`) | только смонтированные слайды — 2 из 8 |

Рядом нашлась вторая дыра, шире первой: регулярка payload'а допускала `\/`
только сразу после схемы, а внутри пути упиралась в обратный слэш. Адрес вида
`https:\/\/cdn.shopify.com\/s\/files\/1\/photo.jpg` — так пишет адрес любой
payload, закодированный в JSON дважды — не находился **вообще**: схема
совпадала, до расширения файла дело не доходило. То есть проход по payload'ам
работал заметно хуже, чем обещал его комментарий.

### Фото

- `snapshot.js` читает страницу, пока она цела: `currentSrc` (это отрисованная
  рендицией, которой нет ни в одном атрибуте), `src`, `srcset`/`data-srcset`,
  зум-атрибуты, `picture > source`, `link[as=image]`, плюс скан содержимого
  `<script>` на адреса картинок. Найденное уходит рядом с разметкой как
  **кандидаты** — сами payload'ы по-прежнему не отправляются, иначе вернулись бы
  те мегабайты, ради которых strip и существует.
- Кандидаты проходят **тот же** фильтр `harvestGalleryImages`, что и адреса из
  разметки: тот же хост, то же родство имён. Поэтому рельс «you may also like»
  на том же CDN в товар не попадает — это проверено отдельным тестом.
- Потолок фотографий 12 → 20, одной общей `MAX_PRODUCT_IMAGES`. До этого три
  места расходились: нормализация 12, импорт 12, а зеркало жёстко
  `min(max, 12)` — найденное сверх двенадцати хранилось ссылкой и не
  скачивалось никогда.

### Цена

Конвертация на фронте уже была (`currency-context.tsx` + `/api/exchange-rates`),
и ломалось не в ней. Ломалось в трёх местах, и главное из них — молчаливый
дефолт: `import-product.ts` подставлял `USD`, когда валюту прочитать не
удалось, а поиск и фильтры сравнивают `price_min` с долларовой суммой напрямую,
не заглядывая в колонку `currency`. Поэтому ₴4 000 приезжали как $4 000, и
заметить это было нечем.

- Новый `src/lib/server/fx.ts`: таблица курсов с базой USD, кэш на час
  (кэшируется и неудача — провайдер, который лёг, лежит не для одного товара),
  фолбэк на 31 валюту. `/api/exchange-rates` переведён на него и больше не
  дублирует ни фетч, ни фолбэк.
- Импорт пересчитывает цену: `price_min`/`price_max` — доллары, `currency` —
  `USD`. Цена магазина сохраняется там, где она правда: в записи ритейлера (по
  ней человек платит) и в новых колонках `source_price`, `source_currency`,
  `fx_rate`, `fx_date` — миграция **019**.
- `normalizeCurrency` больше не подставляет `USD` молча: пустая строка и issue
  «currency not stated». Валюта без курса тоже не выдумывается — цена остаётся
  как в магазине, а строка прогона говорит почему.
- `extractCurrencyFromDisplay` расширен: ₴ ₽ ₹ ₩ ₪ zł Kč CHF 元, слова
  грн/руб/лв, и `CA$`/`A$`/`NZ$`/`HK$`/`S$`/`R$` через lookbehind — иначе `S$`
  внутри `US$` читается как сингапурский доллар. Код ISO принимается только
  рядом с числом: иначе «incl. VAT» становится валютой, а «Try it on» —
  турецкой лирой.
- Расширение присылает видимый текст цены (`4 000 ₴`). На многих магазинах это
  **единственное** место, где валюта названа: в разметке лежит голое число.
- Экран приёмника пишет по каждой странице: `7 photos · 4000 UAH → $97.56`.

## Третий круг: десять пустых полей

Десять жалоб, и ни одна не решалась расширением в одиночку: поля заполняет
сервер, а расширение добывает то, чего в обрезанной разметке нет. Разбито на
шесть частей, каждая закрыта и проверена отдельно.

| Что было | Почему | Что теперь |
|---|---|---|
| Размеры почти никогда | JSON-LD-разбор **всегда** возвращал `sizes: []`; единственным источником были per-site правила | Размеры из четырёх форм структурных данных (`size`, `hasVariant`, `offers`, `additionalProperty` на шести языках) и с отрисованного контрола; словарь размеров решает на сервере |
| Цвет часто пустой | цвет живёт в свотче, а не в разметке | Название с выбранного свотча и из таблицы характеристик, выше по приоритету, чем скан разметки |
| Фильтр цвета пустой | зависит от названия цвета | Ничего не потребовалось: `colorGroupNamesFor` уже раскладывал «Charcoal» → Grey. Появилось название — появился фильтр |
| Описание неполное | `og:description` — обрезанная маркетинговая строка, а настоящее описание в свёрнутом аккордеоне | Читается отрисованный блок (`textContent`, потому что у свёрнутого `innerText` пуст); `og:description` теперь последний, а не второй |
| Материал никогда | брался только JSON-LD `material`, который мало кто заполняет | Из таблицы характеристик и из состава в тексте: состав останавливается на 100%, «20% off» не волокно |
| Бренд иногда | магазин делает дизайнера ссылкой, а не свойством | Плюс таблица характеристик и размеченный на странице бренд |
| Подкатегория никогда | импортёр её **не писал вообще** | Ярлык дерева по имени и по крошкам (`matchSubcategoryLabel`), затем существующий `resolveSubcategory` |
| Категория иногда мимо | только ключевые слова имени и путь URL | Плюс крошки; ярлык дерева важнее совпадения по ключевому слову |
| Стиль никогда | `styleKeywords: []` прошит в импортёре | Вывод по словарю из 13 стилей: имя, описание, материал, ярлык. Не более трёх на товар |
| Цвета не объединялись | CSV-импорт умел, URL-импорт не звал | Ссылки цветового ряда (точное совпадение по `source_url`), а если магазин переключает цвет скриптом — бренд + базовое имя, строго |
| Нет ссылок на тот же товар | сопоставления не было нигде | GTIN (с проверкой контрольной цифры) и бренд+MPN. SKU **не** сшивает магазины — у разных ритейлеров он разный для разных вещей |

Общий принцип тот же, что вытащил фотографии: **расширение смотрит, сервер
решает.** Расширение отдаёт кандидатов — метки размеров как есть, строки
таблицы как напечатаны, крошки, текст описания, — а словари и проверки живут на
сервере, в одном месте. Поэтому «Select size», ссылка на размерную сетку и
«Care instructions» из цветового ряда отсеиваются там же, где отсеивается рельс
рекомендаций.

Две новые миграции: **019** (цена магазина рядом с долларовой) и **020**
(`gtin`/`mpn`/`sku` с индексами). Без них импорт работает как раньше — колонки
сбрасываются по одной, и прогон говорит какие.

## Четвёртый круг: почему «не всегда»

После мержа PR #867 в `goo-fashion` жалобы остались те же — и у большинства
оказалась одна общая причина, которую тесты не ловили: **разметка
`ProductGroup`**.

Так Google с 2024 года просит описывать вещь в нескольких цветах и размерах:
одна группа (имя, бренд, описание) и под `hasVariant` по `Product` на каждый
цвет-размер. Парсер считал каждый вариант отдельным товаром, а страница с
двумя и больше товарами — это «листинг». Листинговый путь брал первую
карточку JSON-LD (например «Wool Coat - Black / S») и **выбрасывал всё, что
прислало расширение**: фото, размеры, цвет, описание, материал, бренд и
валюту из напечатанной цены. Поэтому поля пропадали пачкой и не на всех
магазинах. Тем же путём шли страницы, где товар описан дважды (тема + приложение
отзывов).

Что исправлено (`extract.ts`, `parse-page.ts`):

- `ProductGroup` — один товар. Имя, бренд, описание, материал — с группы;
  цвет, штрихкод — с варианта, который показывает страница (по адресу,
  `?variant=`); размеры и фото — только этого цвета; фото других цветов в
  галерею не попадают; адреса других цветов уходят в группировку по цвету.
- `Product` с `isVariantOf` дополняется брендом и описанием группы.
- `isSimilarTo` / `isRelatedTo` — чужие товары, а не товар страницы.
- Товар, описанный дважды, читается из более полного описания, пробелы
  заполняются из второго.
- Страница, которую прислало расширение, **всегда** читается как товар, и
  никогда не заимствует имя и цену из блока «вам может понравиться».

И одна дыра от двух конфликтующих миграций `019`: в `master` лежат обе,
`019_product_price_usd.sql` (от PR #865) даёт поиску и бюджету стилиста
колонку `price_min_usd` и заполняет её старыми неконвертированными ценами,
а импорт после #867 её не обновлял. Теперь импорт пишет её вместе с
`price_min` (без миграции колонка просто сбрасывается).

Влито в `goo-fashion` как PR #869. Тест: `verification/test-product-group.js` — 33/33.

## Что остаётся за вами

1. **Загрузить расширение и собрать настоящий магазин.** Это принципиально ваш
   шаг: у контейнера серверный IP — ровно тот, от которого мы и уходим. Ходить
   отсюда в живой магазин означало бы делать то, что задача запрещает.
   `chrome://extensions` → Режим разработчика → Загрузить распакованное →
   папка `extension/`.
2. **Приёмник должен быть открыт и залогинен.** Он зовёт API вашей сессией
   Clerk, подменить её я не могу. Вкладку, открытую до установки расширения,
   надо перезагрузить — иначе content script в неё не попадёт.
3. **Домен Студии** в popup по умолчанию `https://www.goo-fashion.com`;
   для локальной разработки впишите свой `http://localhost:3000`.
4. **Прогнать две миграции**: `019_product_source_price.sql` (цена магазина
   рядом с долларовой) и `020_product_codes.sql` (`gtin`/`mpn`/`sku` с
   индексами). Без 019 теряется след конвертации; без 020 не работает сшивка
   одного товара между магазинами — вместо ссылки появится второй товар. Импорт
   в обоих случаях не падает: колонки сбрасываются по одной, и прогон говорит
   какие.

Что я проверить не мог, кроме живого магазина: сам диалог выдачи доступа
(`chrome.permissions.request` требует клика, headless его не даёт) и всё, что

строки (проверена на чистых `productToDb`/`dbToProduct` и на сбросе колонок),
**группировки цветов** и **сшивки товара между магазинами** — их решения
проверены как чистые функции, а запросы вокруг них нет. Всё остальное

профиля Chrome.
